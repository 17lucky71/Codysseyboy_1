# 🔧 [보완 문서] 자동화 파이프라인 확장 및 개선 방안

## 📋 개요

프로젝트 1·2는 과제의 필수 요구사항(Trigger, Action, 조건 분기, 자동 실행 등)을 모두 실제 구현·검증했습니다. 이 문서는 여기서 한 단계 더 나아가, **현재 자동화를 실무 서비스 수준으로 발전시킨다면 어떤 부분을 보완해야 하는지**를 정리한 설계 제안 문서입니다.

⚠️ 아래 내용 중 **모니터링/재시도/대체경로, 모듈화, 코드 확장**은 실제로 구현한 것이 아니라, 현재 구현을 기반으로 도출한 **설계 방안(제안)**입니다. 실제 구현 여부와 혼동되지 않도록 각 항목에 "현재 상태"와 "제안"을 구분해 작성했습니다.

---

## 1. 모니터링 · 재시도 · 대체경로 설계 (보너스 과제 2 관련)

### 1.1 현재 구현 상태

프로젝트 1·2 모두 **정상 실행 경로만** 구현·검증했습니다. Gmail/Google Forms 트리거가 정상 도착하고 Sheets/Discord 액션이 정상 동작하는 경우만 테스트했으며, API 오류나 네트워크 장애 같은 실패 상황에 대한 별도 처리 로직은 구현하지 않았습니다.

### 1.2 모니터링 지표 제안

| 지표 | 확인 방법 |
|---|---|
| 실행 성공/실패 여부 | Make 시나리오의 **Incomplete Executions** 탭에서 실패한 실행 건 확인 |
| 실행 주기 준수 여부 | **History** 탭의 실행 시각 간격이 설정한 스케줄(15분)과 일치하는지 확인 |
| 처리량(Ops) 소진 추이 | 시나리오 상세 화면의 **Scenario Usage** 크레딧 소모량 모니터링 |

### 1.3 재시도 정책 제안 (미구현 · 설계만)

- Make는 모듈별로 **Retry** 옵션을 제공하므로, Google Sheets/Discord 액션에 최대 3회, 지수 백오프(1분 → 5분 → 15분) 재시도를 설정하는 것을 제안합니다.
- Gmail·Sheets API의 일시적 rate limit 오류는 대부분 수 분 내 재시도로 해결 가능하므로, 즉시 실패 처리보다 재시도가 더 안정적입니다.

### 1.4 대체 경로 제안 (미구현 · 설계만)

- Google Sheets 기록이 실패할 경우, 별도의 "임시 저장 시트"에 원본 데이터(발신자/제목/시간)를 먼저 적재하고, 이후 수동으로 본 시트에 옮기는 대체 경로를 제안합니다.
- Discord 알림 실패 시, 동일 내용을 이메일(Gmail Send an Email 모듈)로 대체 발송하는 경로를 추가할 수 있습니다.
- Make의 **Error handler** 기능(모듈에 우클릭 → Add error handler)을 이용하면 이 대체 경로를 시나리오 내에 직접 연결할 수 있습니다.

## 2. 모듈화 전략

### 2.1 현재 구조의 한계

현재 두 프로젝트 모두 Trigger → Router → Action이 **하나의 시나리오 안에 모두 포함된 단일 구조**입니다. 워크플로우가 늘어날수록 같은 로직(예: "긴급 키워드 판별", "Sheets 기록 포맷")을 여러 시나리오에 반복해서 만들어야 하는 비효율이 발생합니다.

### 2.2 모듈화 제안

| 재사용 컴포넌트(안) | 역할 | 재사용 가능 대상 |
|---|---|---|
| "긴급 판별" 서브 시나리오 | 제목/본문 키워드로 긴급 여부 판단 후 결과 반환 | 이메일 자동화 외에 다른 알림 워크플로우에서도 활용 |
| "알림 발송" 서브 시나리오 | Discord/이메일 등 채널에 맞춰 포맷된 메시지 발송 | 여러 워크플로우의 공통 알림 로직 |
| "기록 로깅" 서브 시나리오 | Google Sheets에 표준화된 형식으로 행 추가 | 여러 자동화의 실행 이력 기록에 공통 사용 |

Make에서는 하나의 시나리오를 **Webhook Trigger**로 만들어두면, 다른 시나리오에서 HTTP 모듈로 호출하는 방식으로 위와 같은 서브 시나리오 구조를 만들 수 있습니다. 이렇게 하면 로직을 한 곳에서 수정해도 이를 호출하는 모든 워크플로우에 반영되는 장점이 있습니다.

## 3. 노코드 한계 및 코드 확장 로드맵

### 3.1 이번 과제에서 실제로 느낀 노코드의 한계

- 제목에 특정 키워드가 "포함"되는 단순 조건은 Router 필터로 충분했지만, 복수 키워드 조합이나 정규식 기반의 정교한 조건은 Make의 기본 필터 UI만으로 표현하기 번거로웠습니다.
- 무료 플랜의 Ops(연산) 횟수 제한이 있어, 처리량이 많아지면 자연히 비용이 발생하는 구조입니다.
- 재시도 backoff, 복잡한 예외 분기 같은 세밀한 오류 처리는 노코드 UI 설정만으로는 한계가 있고, 결국 이런 부분은 코드로 구현하는 것이 더 정교합니다.

### 3.2 코드 확장 아이디어 (로드맵)

1. **1단계 (현재)** — Make 기반 노코드 자동화로 핵심 흐름(Trigger → 조건 분기 → 기록/알림) 검증
2. **2단계** — Make의 Webhook 모듈을 이용해, 조건 판별처럼 복잡해질 수 있는 로직만 별도의 서버리스 함수(예: Google Cloud Functions, AWS Lambda)로 이전하고, Make는 Trigger 감지와 최종 액션 호출만 담당
3. **3단계** — 서버리스 함수에서 Gmail API·Sheets API·Discord API를 직접 호출하도록 전환하여, Make 의존도를 낮추고 재시도·로깅·예외 처리를 코드 수준에서 정교하게 구현

### 3.3 확장 시 기대 효과

무료 Ops 제한에 구애받지 않고 처리량을 늘릴 수 있고, 정규식 기반 조건이나 세밀한 재시도 로직처럼 노코드 UI로 표현하기 어려운 부분을 코드로 유연하게 구현할 수 있습니다. 다만 그만큼 유지보수·인프라 관리 부담은 늘어나므로, 실제 전환은 자동화 규모와 팀의 개발 리소스를 고려해 단계적으로 진행하는 것이 합리적입니다.
